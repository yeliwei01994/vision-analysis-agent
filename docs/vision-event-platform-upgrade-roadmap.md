# Vision Event Platform 升级路线图

## 1. 当前能力

系统已具备本地视频上传、抽帧、YOLO 推理、规则事件生成、MySQL 持久化、事件审核、真实证据帧与时间轴展示能力。

当前主要规则为 `person_stay`（人员停留）。事件详情可展示抽帧、检测框、时间点、规则化摘要和审核状态。

## 2. 升级目标

从“识别视频中有什么目标”升级到“根据业务规则发现、复核、处置异常事件”。

核心目标：

- 减少重复事件；
- 支持可配置的业务规则；
- 让审核动作形成可追溯闭环；
- 让模型、队列、证据存储等问题可观测；
- 为多模型、多人协作和后续部署保留扩展空间。

## 3. 优先级总览

| 优先级 | 项目 | 价值 | 建议阶段 |
| --- | --- | --- | --- |
| P0 | 后端事件合并 | 消除同一视频中大量重复卡片 | 第一阶段 |
| P0 | 可视化区域/越线规则 | 形成真实业务监控能力 | 第一阶段 |
| P1 | 审核闭环与操作记录 | 让确认/忽略可追责、可统计 | 第二阶段 |
| P1 | 证据帧生命周期优化 | 控制磁盘占用、提高证据可读性 | 第二阶段 |
| P1 | 多条件事件检索与导出 | 提升事件运营效率 | 第二阶段 |
| P2 | 任务与模型可观测性 | 快速定位性能、失败、积压问题 | 第三阶段 |
| P2 | 目标跟踪能力 | 提升“停留”“徘徊”等连续行为判断准确度 | 第三阶段 |

## 3.2 事件数据模型升级

为支撑后续规则、审核、检索和分析，事件对象需要逐步补充以下字段：

| 字段 | 用途 | 来源 |
| --- | --- | --- |
| `id`、`job_id` | 事件与视频关联 | 已有 |
| `event_type`、`rule_version` | 规则标识与历史兼容 | 已有 |
| `start_time_ms`、`end_time_ms` | 事件时间范围 | 已有 |
| `severity`、`status` | 风险与审核状态 | 已有 |
| `confidence`、`detection_count`、`max_confidence` | 事件质量指标 | Worker 聚合 |
| `objects`、`track_ids` | 检测类别与轨迹 | YOLO/跟踪器 |
| `evidence.frames` | 帧时间、图片 URL、检测框 | 已有 |
| `zone_id`、`geometry_snapshot` | 触发区域与当时规则快照 | 规则引擎 |
| `analysis` | LLM 或规则化解释 | 已有/可扩展 |
| `review_summary` | 最终审核结果摘要 | 审核记录聚合 |

任何事件列表接口都应继续返回摘要字段；详情接口可额外返回完整证据帧和审核历史，避免列表查询加载过多 JSON。

## 4. 第一阶段：规则能力与事件去重

### 4.1 后端事件合并

**问题**：当前同一目标在连续帧中被检测到时，可能生成多个近似事件；前端分组只能改善显示，不能减少数据库记录和审核工作量。

**方案**：在 Worker 中按以下维度聚合候选事件：

- `job_id` 相同；
- `event_type` 相同；
- 目标类别相同；
- 时间间隔小于配置阈值，例如 3 秒；
- 有追踪 ID 时，优先按相同 `track_id` 合并。

合并后的事件保留：开始时间、结束时间、所有命中帧、平均置信度、最高置信度帧和检测次数。

**验收标准**：同一视频中连续出现的同类目标只生成一个可审核事件；事件详情仍可查看全部证据帧。

### 4.2 可视化区域规则

**目标**：让用户可在视频画面中圈定区域或画一条线，再配置对应规则。

首批规则建议：

- 区域入侵：目标进入指定多边形区域；
- 人员停留：目标在区域内持续超过指定时长；
- 人数超限：区域内人员数超过阈值；
- 越线：目标穿越指定线段。

**数据结构建议**：在 `event_rules` 中增加 `geometry_json`、`threshold`、`enabled` 字段。几何坐标使用 0–1 的比例坐标，不依赖视频分辨率。

**验收标准**：用户可创建规则、在视频画面中定义区域、上传视频后得到对应事件。

## 5. 第二阶段：审核闭环与运营能力

### 5.1 审核闭环

确认和忽略不应只是状态切换。建议新增：

- 审核备注；
- 审核人；
- 审核时间；
- 处置结果，例如“已通知”“误报”“已处理”；
- 事件状态流转记录。

新增 `event_reviews` 表，每一次人工操作作为独立审计记录保存。

**验收标准**：能在事件详情中查看所有审核记录，并可按审核人和状态筛选。

### 5.2 证据帧优化

当前会保存命中帧。建议按事件保留：

- 首次命中帧；
- 置信度最高帧；
- 最后命中帧；
- 可选：每隔固定秒数的一张代表帧。

同时生成带框标注的 JPEG 作为预览，原始帧保留给精细查看。为证据设置每事件最大图片数与定期清理策略。

**验收标准**：单事件证据可读、磁盘增长可控，删除事件时连带删除其证据目录。

### 5.3 检索和导出

事件列表增加筛选：视频任务、时间范围、规则、目标类别、审核状态、严重等级、置信度。

支持导出 CSV：事件编号、视频、时间段、规则、目标摘要、置信度、审核结果、审核备注。

## 6. 第三阶段：稳定性与识别质量

### 6.1 可观测性

在管理页面增加：

- 上传/处理任务成功率与失败原因；
- Redis 队列积压数量；
- 每个视频抽帧数量、YOLO 总耗时、平均单帧耗时；
- 模型版本与规则版本；
- 证据目录磁盘占用。

Worker 日志建议统一输出 `job_id`、耗时、帧数、事件数和错误类型。

### 6.2 目标跟踪

当前无稳定追踪 ID 时，多个不同目标可能被当成同一轨迹。接入 ByteTrack 或 DeepSORT 后可改善：

- 同一人停留时长统计；
- 多人场景中的独立事件；
- 徘徊、离开、重复进入等连续行为规则；
- 事件合并准确度。

## 7. 建议实施顺序

1. 后端事件合并；
2. 区域规则数据模型与规则编辑页；
3. Worker 支持区域入侵与人数超限；
4. 审核记录与备注；
5. 证据帧精简、标注图和清理策略；
6. 条件检索与 CSV 导出；
7. 任务/模型监控面板；
8. 接入目标跟踪模型。

## 8. 本地测试清单

- 上传含人员、船只等目标的视频，确认 Worker 生成证据文件；
- 用连续人员片段验证事件合并数量；
- 配置区域后验证区域内外目标的事件差异；
- 确认、忽略并填写备注，检查 MySQL 审核记录；
- 删除事件，检查事件记录与 `media/evidence/<event-id>` 同时清理；
- 模拟 YOLO 不可用、Redis 不可用、视频损坏等失败场景；
- 检查长视频处理时的抽帧数量、证据图片数量和磁盘增长。

## 9. 成功标准

完成前三项后，系统应能回答：

> 哪个视频、什么时间、什么目标、在什么区域、触发了什么规则、证据是什么、谁如何处置了它。

这会使项目从 YOLO 演示应用，升级为可用于实际视频事件运营的原型系统。

## 10. 可执行任务分解

### 阶段 A：事件质量与证据（建议优先完成）

#### A1. 后端事件合并

- 修改 Worker：按视频、规则、类别、轨迹、时间间隔聚合候选事件；
- 修改数据库：为事件增加检测次数、最大置信度、合并来源数量；
- 修改 API：事件列表返回合并后的摘要；
- 修改前端：保留“多个片段”的展开入口，而不是用前端掩盖重复记录；
- 测试：同一人连续 10 秒出现只产生一个事件，离开超过阈值后产生新事件。

#### A2. 证据帧代表帧策略

- Worker 不再无限保存全部命中帧；
- 每个事件至少保留首帧、最高置信度帧、末帧；
- 可配置最大帧数和固定采样间隔；
- 使用 OpenCV 或 Pillow 生成带检测框、类别、置信度的预览图；
- 删除事件时删除对应证据目录；
- 测试：长视频不会无限增长，详情仍能呈现完整事件过程。

#### A3. 证据媒体可靠性

- API 为图片增加正确 MIME 类型、缓存控制和不存在时的明确错误；
- 前端图片加载失败时显示“证据文件不可用”和重新加载按钮；
- 增加媒体目录健康检查、剩余磁盘空间提示；
- 为未来对象存储定义 `EvidenceStorage` 抽象，避免业务逻辑直接依赖本地磁盘。

### 阶段 B：业务规则体系

#### B1. 区域与线段编辑器

- 前端在视频/抽帧画布上支持画矩形、多边形和线段；
- 统一使用归一化坐标（0–1）；
- 保存区域名称、颜色、启用状态、关联规则；
- 支持编辑、复制、删除、预览和规则版本号；
- 验收：同一规则在不同分辨率视频上区域位置一致。

#### B2. 区域入侵与人员停留

- Worker 判断目标中心点或底部中心点是否进入区域；
- 停留规则记录进入时间、最后出现时间、累计停留时长；
- 支持类别、最小置信度、最短停留时长、严重等级配置；
- 事件详情显示触发区域、规则参数快照和目标轨迹。

#### B3. 人数超限、越线和目标消失

- 人数超限：按区域统计稳定轨迹数量，避免同一人重复计数；
- 越线：判断轨迹跨越线段方向，支持进入/离开方向；
- 目标消失：指定区域中目标从“存在”变为“持续缺失”；
- 每种规则均需独立单元测试和真实视频验收集。

### 阶段 C：审核与事件运营

#### C1. 审核工作流

- 状态扩展为：待复核、确认、忽略、处理中、已处置、已关闭；
- 确认/忽略时可填写备注、选择处置结果；
- 保存审核人、时间、旧状态、新状态和备注；
- 详情页展示审核时间线；
- 前端增加成功提示、失败原因、禁用重复提交和状态过渡动画。

#### C2. 多条件检索、分页和导出

- 筛选项：视频、规则、区域、类别、状态、严重等级、置信度、时间范围、审核人；
- 后端实现可组合查询、排序、分页，避免一次返回全部事件；
- CSV 导出使用当前筛选条件；
- 列表卡片展示缩略图、中文摘要、规则版本、审核状态和时间范围；
- 验收：一万条事件仍可按条件快速加载首屏。

#### C3. 事件关联与报告

- 关联同一视频、同一区域、同一轨迹的事件；
- 自动生成事件报告：视频名称、时间线、证据图、规则、审核结论；
- 支持导出 HTML/PDF（本地阶段可先导出 HTML）；
- LLM 可选参与报告说明，但系统在没有 LLM 时必须保留规则化摘要。

### 阶段 D：模型质量与系统运维

#### D1. 目标跟踪与模型评估

- 接入 ByteTrack 或 DeepSORT；
- 记录模型、跟踪器、规则的版本；
- 建立小型标注视频集，统计检测准确率、事件准确率、误报率、漏报率；
- 支持置信度阈值和规则参数 A/B 对比。

#### D2. 运行监控与故障处理

- Worker 显示队列长度、正在处理任务、处理帧数、平均耗时；
- 任务失败保存错误分类：视频解码、YOLO、Redis、MySQL、证据保存；
- 增加重试次数、死信队列和可手工重跑任务；
- 仪表板显示 API、Worker、YOLO、Redis、MySQL、磁盘空间健康状态。

#### D3. 数据治理与部署准备

- 视频、证据、事件、审核数据分别定义保留期限；
- 定期清理已删除事件的孤儿证据目录；
- MySQL 备份/恢复脚本；
- 把本地 `MediaStorage` 替换为对象存储时保持 URL 契约不变；
- 为后续多用户添加身份认证、角色权限和数据隔离。

## 11. 阶段交付物与验收

| 阶段 | 最小交付物 | 必须通过的验收 |
| --- | --- | --- |
| A | 合并事件、代表帧、可靠证据访问 | 新视频仅生成合理数量事件；每条事件可打开图片和时间轴 |
| B | 区域编辑器与三类新规则 | 配置区域后，区域内外同一目标得到不同事件结果 |
| C | 审核历史、筛选、导出 | 人工操作可追溯；按条件检索与 CSV 内容一致 |
| D | 跟踪、监控、失败重试 | 可定位任一失败任务的原因；长时间运行无证据目录泄漏 |
